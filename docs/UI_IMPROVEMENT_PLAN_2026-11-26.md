# PuTTYPlus UI/UX 提升计划（2026-11-26）

> **状态**：实施计划，尚未开始产品代码修改。  
> **输入**：[全界面 UI/UX 审核报告](UI_REVIEW_2026-11-26-全界面.md)。  
> **代码基线**：`e2f1efa`。  
> **计划目标**：在不推倒现有优秀界面的前提下，修复关键操作不可达、可读性不足、窗口结构失衡、错误恢复不完整和视觉语言不一致的问题。

---

## 1. 结论与实施原则

当前项目不是“没有设计”，而是**关键体验被少数阻断问题拖累**。编辑器、数据库数据页、Docker 文件页已经形成值得保留的设计语言；本轮不应把它们重做成另一套风格。

提升顺序必须是：

1. **先保证看得见、点得到、看得清**；
2. **再保证出错后能恢复**；
3. **再统一空态、窗口和视觉节奏**；
4. **最后做一致性打磨与自动化守门**。

### 1.1 设计目标

- **专业**：像基础设施工具，不像营销页面或功能演示稿。
- **紧凑**：默认窗口内优先呈现高密度工作内容，不用大面积装饰挤占操作区。
- **可信赖**：连接状态、失败原因、危险操作后果和当前进度必须明确。
- **可恢复**：错误提示关闭后，用户仍能找到原因与恢复入口。
- **一致**：相同状态、相同动作、相同层级在不同页面使用相同表达。
- **可访问**：明暗主题均可读，键盘可完成主流程，图标按钮有名称与 tooltip。

### 1.2 非目标

本计划**不包含**以下内容：

- 不更换 GTK、终端引擎、SFTP/数据库/Docker 后端架构。
- 不重做编辑器、数据库结果网格、Docker 文件页的核心布局。
- 不引入新的品牌字体、插画体系或装饰性动效。
- 不把桌面端照搬成移动端布局；不为了“触屏友好”把专业工具改成大色块卡片。
- 不把 Docker 的原始英文错误全部藏掉；“说人话”与“保留原文”必须同时成立。
- 不自动重试危险写操作，不用弹窗替代持久的页面状态。
- 不在本阶段打包、安装、发布或修改用户真实配置。

### 1.3 不可破坏的项目既有决策

实施时必须保留：

- 欢迎页不重新增加“新建连接”大按钮；统一新建入口仍以侧栏/页签菜单为准。
- 传输完成不自动弹窗；通知不可用时只写状态栏。
- 数据库连接不在工作台顶部新增第二套连接表单。
- 容器详情、日志、文件各使用独立工具窗，关闭时停止对应流。
- 刷新要保留用户选中；写操作后的刷新请求不能被“正在刷新”守卫静默吞掉。
- 进度、呼吸动画、状态变化不得整表 `queue_draw()`。
- 用户可见文案走 `tr()` / `trf!()`，英文界面必须有对应译文。

## 3. 设计系统规范

### 3.1 视觉语言

保持“安静的桌面工作台”：

- 信息密度高，但通过分组、对齐和留白形成层级。
- 卡片只用于真正需要独立边界的内容；列表和表单不要普遍卡片化。
- 不用大号品牌图标填补空白。
- 不用阴影制造层级；普通容器可使用 1px 边框和表面色差。
- 动效只用于反馈：连接中、传输中、刷新中、状态切换；不做纯装饰动画。

### 3.2 颜色与语义

| 角色 | 规则 |
|---|---|
| 正文 | 使用主题前景色，普通文字在所在表面上 ≥4.5:1 |
| 次要文字 | 使用现有 `dim_hex()` / `dim-label`，仍须 ≥4.5:1 |
| 主按钮 | `accent_bg` + `accent_fg`，两者按主题解析并自动校验 |
| 危险按钮 | `danger_bg` + `danger_fg`，不能直接复用浅色主题的错误色到深色实心按钮 |
| 成功/警告/错误 | 使用 `theme::State`；颜色之外必须有文字或图标含义 |
| 选中态 | 文本、边框、焦点环均可辨认；不能只靠淡色底 |
| 禁用态 | 可以降低强调，但 tooltip 必须说明为什么不能操作 |

实施要求：

1. 扩展现有 [`theme::contrast_ratio`](../src/theme.rs) 与 [`theme::dim_for`](../src/theme.rs)，不要另写第二套 WCAG 算法。
2. 先修正前景色；若仍然不足，再在保持色相的前提下调整实心背景色。
3. 深色主题不能简单把文字改成白色就宣布通过；审核实测该组合仍只有 4.12:1。
4. CSS 令牌与 cairo/markup 使用的 hex 必须来自同一语义来源，避免两套颜色漂移。
5. 每个主题至少覆盖 default、hover、pressed、checked、focus、disabled 六种状态。

### 3.3 间距、密度与尺寸

采用现有 `density` 机制，不新造一套全局布局引擎。

| 层级 | 建议尺度 | 用途 |
|---|---|---|
| 微间距 | 4px | 图标与文字、紧凑标签内部 |
| 组件间距 | 8px | 同组按钮、表单项内部 |
| 分组间距 | 12px | 相关控件组之间 |
| 区块间距 | 16px | 表单分区、卡片区块 |
| 页面留白 | 24px | 工具窗内容边缘、欢迎页内容区 |

- 行高、控件高度随现有密度档位变化，不写死唯一像素值。
- 桌面端图标按钮以现有紧凑尺寸为准，但必须留出足够命中区域；不为追求 44px 把高密度表格工具栏撑坏。
- 长文本使用省略号 + tooltip；错误原因和表单说明使用 wrap + 限宽。
- 数字列右对齐，技术值使用等宽字体；同一列的单位和小数位保持一致。

### 3.4 表面层级

浅色主题至少区分三层：

1. **窗口底面**：应用背景；
2. **面板/列表面**：文件列表、数据库对象树、设置页；
3. **卡片/输入面**：需要独立边界的内容。

深色主题反向保持同样可辨识，不能只靠边框亮度。优先扩展现有 `.pp-card`、`.pp-pill`、`.pp-kbd`、`.pp-mono`，不新增同义类。

### 3.5 状态模型

每个数据区域必须能表达以下状态，且不能互相覆盖：

- **加载中**：保留上次内容时显示局部指示，不展示“空”；
- **空**：没有数据，提供下一步；
- **失败**：分类原因 + 建议 + 原文详情 + 恢复入口；
- **成功**：明确结果，短暂反馈后回到稳定状态；
- **部分成功**：分别给出成功与失败数量，不只说“完成”。

### 3.6 窗口模式

| 类型 | 规范 |
|---|---|
| 工作台页面 | 主窗口内的页签，随会话走；不额外开重复窗口 |
| 表单对话框 | 模态、有父窗口、底部动作固定、矮屏可滚动、高屏不过度拉高 |
| 工具窗口 | 非模态、单例、记尺寸、可关闭重开；关闭时停止后台流 |

表单窗口的高度由**当前内容和工作区**决定，不再回到固定 405px，也不能永久按最高页撑满。

## 5. 阶段 0：基线与守门

### UI-00 建立可复现的界面基线

**对应问题**：所有任务的验收基础。  
**优先级**：P0 前置。  
**工作量**：M。  
**依赖**：无。

#### 现状

已有许多冒烟，但覆盖的是单点行为；缺少统一的窗口几何、主题、键盘和 GTK 健康检查。仅靠截图容易受字体、窗口管理器和 Xvfb 尺寸影响。

#### 目标

建立一套“几何断言为主、截图为辅”的基线，后续每项任务都能证明自己修复了用户可见问题。

#### 实施步骤

1. 固定参考环境：X11、Cairo、`NO_AT_BRIDGE=1`，记录 GTK、字体和显示缩放。
2. 为每类界面建立 1200×780、1024×700、1366×768 三个尺寸的测试宿主。
3. 统一浅色、深色、高对比三套主题。
4. 整理现有 example 的职责，避免新建重复测试：
   - 表单：`dlgsize_smoke`、`authpage_smoke`、`fwdpage_smoke`、`sesspage_smoke`；
   - Docker：`docker_actioncol_smoke`；
   - 数据库：`db_empty_smoke`；
   - 欢迎页：`welcome_cards_smoke`；
   - 镜像：`mirror_smoke`；
   - 对比度：`contrast_smoke`；
   - 回放：现有 `rec_*` 或独立回放窗口冒烟。
5. 定义公共测试口径：控件必须已映射、窗口已 `present()`、主循环已泵送后再量几何。
6. 截图只作为人工视觉证据，不做脆弱的全图像素 diff；字体差异不应误报功能回归。
7. 测试启动时清理测试标签、探针对象和临时配置，避免一次失败污染后续运行。

#### 主要文件

- [`.github/workflows/ci.yml`](../.github/workflows/ci.yml)
- [`docs/UI_CHECKLIST.md`](UI_CHECKLIST.md)
- 相关 `examples/*_smoke.rs`

#### 测试与验收

- 所有新断言在修复前能复现失败，修复后通过。
- 新断言必须做一次反向验证：临时恢复坏行为，确认测试确实变红。
- 测试不依赖真实服务器；真库探针仍只使用允许范围。
- CI 日志只保留运行输出，编译输出单独丢弃，失败时先发人眼可读尾部。

#### 风险与回滚

- 风险：测试宿主尺寸与真实窗口管理器的装饰尺寸不同。
- 缓解：使用 monitor workarea，并在真实主窗口复验。
- 回滚：测试设施与产品改动分开提交，可单独撤回。

## 6. 阶段 1：P0 阻断问题

### UI-01 修复实心按钮与错误色的对比度

**对应问题**：P0-2。  
**优先级**：P0。  
**工作量**：M。  
**依赖**：UI-00。

#### 现状与根因

[`theme.rs`](../src/theme.rs) 的通用规则把 `color: @pp_fg` 直接设在按钮及其内部 `label` 上；`button.pp-primary` 只设置了按钮容器颜色，内部 Label 不继承该颜色。

当前只显式处理了图片：

```css
button.pp-primary image { color: @pp_on_accent; }
```

缺少内部 Label 的对应规则。实测浅色主按钮约 3.24:1、深色约 3.08:1；深色危险按钮白字也只有 3.96:1。

#### 目标

- 所有实心按钮文字 ≥4.5:1。
- hover、pressed、checked、focus 不破坏对比度。
- 深色主题的强调色和错误色仍然有明确品牌/语义，不靠“默认黑字”蒙混过关。
- 图标按钮的关键图形 ≥3:1，且有 tooltip 与可访问名称。

#### 实施步骤

1. 为 `.pp-primary`、`.suggested-action`、危险按钮的内部 `label` 与 `image` 显式设置前景色。
2. 检查是否还有同类容器：选中按钮、切换按钮、标签栏动作、菜单主操作。
3. 在主题解析阶段计算 `accent_fg` / `danger_fg`；不满足阈值时调整语义背景，而不是只改文字。
4. 将同一语义色输出给 CSS 与 cairo/markup 使用方。
5. 为英文界面同步所有新增或修改的提示文案。
6. 不用 `!important` 压制问题；优先修正选择器和颜色来源。

#### 主要文件

- [`src/theme.rs`](../src/theme.rs)
- [`src/i18n_en.rs`](../src/i18n_en.rs)
- `examples/contrast_smoke.rs`

#### 测试与验收

- 对浅色、深色、高对比分别计算实际按钮背景与 Label 前景。
- 正常态、hover、pressed、checked 均通过；disabled 单列说明，不伪装成通过。
- 主按钮和危险按钮同时覆盖，不只测一个蓝色按钮。
- 截图确认颜色变化没有破坏选中态和焦点态。
- 搜索项目中其他“容器设色、内部 Label 未设色”的同类问题。

#### 风险与回滚

- 风险：系统主题 accent 与自定义颜色差异较大，自动选色可能改变品牌感。
- 缓解：只在对比度不足时调整，保留色相；先出三主题对照截图再收口。
- 回滚：颜色解析与 CSS 规则独立提交，可恢复上一组语义令牌；不得回滚到已确认不可读的状态。

### UI-02 Docker 列表响应式列策略

**对应问题**：P0-1。  
**优先级**：P0。  
**工作量**：M～L。  
**依赖**：UI-00；最终视觉在 UI-08 后复查。

#### 现状与根因

[`dockerui.rs`](../src/panel/dockerui.rs) 六列最小宽合计约 1019px，操作列另需约 120px。默认 1200×780 主窗口扣除侧栏、边框、padding 和滚动条后，操作列落在地平线之外。

当前镜像、端口、状态、资源四列同时 expand，窄窗口下没有明确的退让顺序。

#### 目标

- 名称、状态、操作是**始终保留**的三项。
- 默认窗口完整显示操作列，图标不被裁切。
- 1024×700 下仍能完成启停、重启、详情等主任务。
- ID、资源、端口、镜像按内容区宽度逐级退让，不随机消失。
- 保留 compose 项目行、4 颗项目操作、状态可用性、排序、刷新选中和 pending refresh。

#### 推荐布局分档

以下为分配策略，不是写死的最终像素：

| 内容区宽度 | 保留列 | 退让列 |
|---|---|---|
| 宽 | 名称、ID、镜像、端口、状态、资源、操作 | 无 |
| 中 | 名称、镜像、端口、状态、操作 | ID、资源收入详情 |
| 窄 | 名称、镜像、状态、操作 | ID、端口、资源 |
| 极窄 | 名称、状态、操作 | 其余列收入详情或隐藏 |

实施约束：

- 用实际 allocation 宽度切换，不用窗口原始宽度猜测。
- 切换加滞回，避免在阈值附近反复显隐。
- 用户正在拖动列宽或弹出菜单时不要立即重排。
- 图标组左对齐；画与命中继续共用 `group_offset()` / `hit_index_at()` 的算术。

### UI-07 Docker 文件错误分类与原文详情

**对应问题**：P1-4。  
**优先级**：P1。  
**工作量**：M。  
**依赖**：UI-00；颜色依赖 UI-01。

#### 现状与根因

[`dockerui.rs`](../src/panel/dockerui.rs) 的 `files_err_zh()` 只处理“镜像没有 ls”一种情况，其余 Docker/OCI 原文直接显示。权限不足、容器停止、只读文件系统、超时、守护进程不可达等错误缺少一致的中文建议。

#### 目标

- 界面主提示使用中文分类与下一步建议。
- 原始错误保留在“详情”中，便于排查。
- 不用模糊的“操作失败”覆盖所有情况。
- 同一分类在列表、上传、下载、查看内容中保持一致。

#### 错误分类建议

| 类别 | 典型特征 | 建议 |
|---|---|---|
| 权限不足 | permission denied、operation not permitted | 检查容器用户与文件权限 |
| 容器未运行 | container is not running、is stopped | 先启动容器或进入运行中的容器 |
| 只读文件系统 | read-only file system | 更换挂载/权限，不以管理员身份盲目重试 |
| 路径不存在 | no such file or directory | 刷新目录并检查路径 |
| 命令缺失 | executable file not found | 说明缺少所需命令，建议进入终端处理 |
| 超时 | timed out、timeout | 提示稍后重试或检查容器状态 |
| Docker 不可达 | cannot connect to the docker daemon | 检查 Docker 服务与当前账号权限 |
| 未知 | 无法可靠分类 | 显示“操作未完成”并保留原文 |

分类必须使用**结构化错误或明确特征**，不能仅凭文件名中的关键词猜原因。

#### 实施步骤

1. 将纯分类逻辑抽成可单测函数，输出 `kind + advice + raw`。
2. 内联状态显示简短建议；详情弹窗显示完整原文。
3. 上传/下载失败不要自动覆盖原文件或重复执行。
4. 所有新增文案补英文翻译。
5. 保持空目录与失败的区分：退出码为 0 的 0 行仍是合法空目录。

#### 测试与验收

- 每类至少一条真实形态的样本，含 Docker 29 的多行错误与 `exit status N` 尾行。
- 中文主提示不含未翻译的英文残句；原文详情完整保留。
- 未知错误不瞎猜权限或网络原因。
- 失败不会清空当前目录或把路径栏推进到错误目录。
- 权限失败有可执行的下一步，而不是只写“失败”。

#### 风险与回滚

- 风险：关键词过宽导致误分类。
- 缓解：优先使用退出码/错误类型；未知分类保持保守。
- 回滚：只恢复内联文案展示，不影响文件操作与解析逻辑。

**依赖**：UI-08。

#### 现状

[`erview.rs`](../src/panel/erview.rs) 在单表或表间无关系时仍显示固定大画布，只有表框和状态行，用户看到的是大片空白。

#### 目标

- 不伪造关系，不自动连接表。
- 无关系时解释当前状态，并提供“查看表 / 新建关系 / 返回对象树”等真实动作。
- 用户仍可进入画布调整布局；空态不能隐藏已有表。

#### 实施步骤

1. 区分三种情况：没有表、只有一张表、多表但 0 条关系。
2. 无表使用标准空态；单表显示表摘要与下一步；多表无关系显示紧凑说明。
3. 默认优先展示有用信息，画布作为可进入的工作区，而不是用空白画布充当状态。
4. 保持拖动、缩放、双击表框看数据等现有能力。
5. 不新增数据库写操作；所有按钮只导航或打开已有编辑器。

#### 测试与验收

- 三种状态标题与解释不同。
- 单表仍显示真实表名/字段摘要。
- 主 CTA 产生可见结果，不出现“点了没反应”。
- 进入画布后拖动和双击仍正常。
- 不生成假边，不修改数据库。

#### 风险与回滚

- 风险：隐藏默认画布改变老用户习惯。
- 缓解：提供明确“打开画布”入口；不删除画布功能。
- 回滚：状态层可单独移除。

### UI-11 通知中心与传输队列增强分组和后续动作

**对应问题**：P2-4。  
**优先级**：P2。  
**工作量**：L。  
**依赖**：UI-08。

#### 现状

[`notify.rs`](../src/notify.rs) 的通知中心是平铺时间列表，缺少级别和动作；[`queue.rs`](../src/panel/queue.rs) 信息完整，但失败项处理入口不够突出。

#### 目标

- 通知按级别与批次分组，用户先看到需要处理的事项。
- 队列提供成功/失败/取消摘要和失败筛选。
- 通知的“查看明细”打开队列并定位失败，不只是打开一个普通窗口。
- 保持“传输完不自动弹窗”的硬约束。

#### 实施步骤

1. 为 `Entry` 增加进程内语义：级别、批次/来源、可用动作；不新增持久化敏感数据。
2. 通知行使用文字/图标表达级别，不只靠颜色。
3. 传输类通知默认动作打开队列；失败批次定位到失败筛选。
4. 队列顶部增加只读摘要：完成、失败、跳过、取消。
5. 增加“全部 / 进行中 / 失败”筛选，不自动重排用户正在传输的行。
6. 失败行提供“查看原因”“复制路径/错误”等低风险动作。
7. “重新传输”作为独立子项：仅在源、目标、连接仍有效时可用，执行前说明覆盖风险；不得自动重试。
8. 通知正文仍不包含文件内容、密码或凭据。

#### 测试与验收

- 全成功、部分失败、全失败、取消、全部跳过各有正确摘要。
- 点击通知才打开汇总视图；通知服务拒绝时不弹窗。
- 失败筛选只显示失败项，清除筛选后原顺序稳定。
- 重试不会隐式覆盖文件；不可用时按钮灰掉并说明原因。
- 关闭队列不取消传输；取消操作仍走既有确认/状态机。
- 无整表重画和主线程阻塞。

#### 风险与回滚

- 风险：批次元数据与旧调用不匹配；重试带来覆盖风险。
- 缓解：先上线分组/筛选/详情，重试单独提交并保守启用。
- 回滚：通知展示层可恢复平铺列表，传输逻辑不变。

### UI-12 目录镜像默认宽度与时间列

**对应问题**：P2-5。  
**优先级**：P2。  
**工作量**：S～M。  
**依赖**：UI-08。

#### 现状

[`mirrorui.rs`](../src/panel/mirrorui.rs) 默认 860×560，五列中只有相对路径 expand，两个时间列在真实主窗口内容区偏紧。独立测试窗口的宽度不能代表实际使用环境。

#### 目标

- 默认宽度下动作、相对路径、大小、两个时间均可读。
- 窄窗口优先保留动作与路径，时间列可缩短格式或退让，不撑破对话框。
- 删除远程多出文件仍默认关闭，写操作仍二次确认。

#### 实施步骤

1. 在真实主窗口以默认尺寸和窄尺寸各量一次，不用独立 860px 宿主代替结论。
2. 给各列设置语义 min width；相对路径继续 expand。
3. 时间使用统一、紧凑格式；完整时间放 tooltip 或详情。
4. 必要时允许对话框在屏幕允许范围内适度加宽，而不是让五列互相挤压。
5. 保持默认不删除、类型冲突不动、预览后执行等安全行为。

#### 测试与验收

- 默认和窄尺寸下时间不被截成不可读的省略号。
- 所有列头、滚动条、底部按钮可见。
- 空目录与扫描失败不混淆。
- 写操作确认和默认删除开关不变。

#### 风险与回滚

- 风险：加宽对话框在小屏上出界。
- 缓解：按 workarea 限宽，允许局部滚动。
- 回滚：列宽与默认尺寸分开提交。

### UI-13 核实并修复快速命令空态键盘行为

**对应问题**：P2-6（待核实）。  
**优先级**：P2。  
**工作量**：S；若确认修复为 M。  
**依赖**：UI-00。

#### 现状

[`quickcmd.rs`](../src/panel/quickcmd.rs) 把空态 Label 作为 ListBox 行 appended。`selected()` 已用索引范围避免越界，因此**不能仅凭代码外观判定功能损坏**。

#### 实验步骤

1. 空列表打开对话框，记录初始焦点。
2. Tab 是否经过占位 Label；方向键是否选中占位行。
3. 在占位行按 Enter、空格，是否触发意外动作。
4. “编辑/删除”是否保持禁用，tooltip 是否说明原因。
5. 新建一条后，占位行是否消失，焦点是否落到新行。
6. 删除最后一条后，焦点是否回到合理位置。

#### 处理方案

- 若行为完全正确：只补一条回归测试，不改产品代码。
- 若占位行可获得焦点/被选中：把空态移到 ListBox 外，使用 `emptystate`；主 CTA 直接触发“新建”。
- 若只是视觉问题：调整 `dim-label` 与间距，不改变选择模型。

#### 测试与验收

- 空态不是可选数据行。
- 编辑/删除在无条目时不可用且原因明确。
- 新建、编辑、删除最后一条后焦点稳定。
- 不写入用户真实快速命令配置。

#### 风险与回滚

- 风险：把正常行为误修成新问题。
- 缓解：先完成行为实验，以证据决定是否修改。
- 回滚：空态展示层可独立恢复。

## 11. 测试策略

### 11.1 分层

| 层级 | 适合验证 | 不适合验证 |
|---|---|---|
| 纯函数单测 | 颜色计算、错误分类、状态摘要、布局分档决策 | GTK 实际几何、真实点击、焦点 |
| GUI example | 已映射控件几何、真实坐标命中、按钮敏感态、弹窗开关 | 真库/真服务器全链路 |
| 集成冒烟 | SSH/SFTP、数据库、Docker 通道与自愈 | 高频视觉回归 |
| 人工截图审查 | 层级、密度、字体、图标观感 | 自动防回归 |

**单测中不得初始化 GTK。** GTK 断言必须放独立 example，在主线程运行。

### 11.2 新断言的要求

- 测外部可见量：实际 allocation、可见范围、绘制次数、命中行、计算后颜色。
- 不只测模型行数、CSS 字符串、标志位或“调用过某个函数”。
- 先证明坏行为会失败，再接受新断言。
- 测试前清理上次失败遗留的标签、探针对象和临时配置。
- 隔离 `PUTTYPLUS_SETTINGS_INI`、`PUTTYPLUS_CONN_INI`、`PUTTYPLUS_DB_INI`、`PUTTYPLUS_HIST_INI`、`PUTTYPLUS_COLS_INI`、`PUTTYPLUS_RECENT_INI`、`PUTTYPLUS_VAULT`。

### 11.3 截图策略

- 每个页面至少一张默认尺寸浅色图、一张深色图；问题页面加窄尺寸图。
- 截图前 `present()`、泵送主循环，必要时 `xdotool windowraise`。
- 记录提交号、主题、窗口尺寸、缩放和是否连接真实数据。
- 不以像素级 diff 作为唯一门禁；以几何、颜色计算和人工视觉审查为主。

## 12. 性能、安全与兼容红线

### 12.1 性能

- 进度、动画、状态刷新只标脏受影响行。
- 不因主题或响应式列切换在每帧重建整张列表。
- 不在 GTK 主线程同步等待 SSH、SFTP、数据库或 Docker 网络请求。
- 列宽切换、错误分类、状态汇总必须是轻量计算。
- 传输稳态继续用实际单元格绘制次数和主线程迭代时间守门。

### 12.2 安全

- 通知、错误详情、日志、截图中不得出现密码、私钥内容或会话秘密。
- 原始错误可以显示主机/路径，但测试证据入库前必须替换为占位值。
- 重新传输、删除、覆盖等动作必须明确后果；默认焦点放在取消。
- 不通过提高权限解决权限类错误提示。

### 12.3 兼容性

- 不改变 PuTTY 命令行参数、退出码、askpass 协议。
- 不改变远程路径 POSIX、本地路径平台原生的既有语义。
- 不修改用户配置格式；若确需新增窗口尺寸键，使用可选读取与旧值回退。
- Windows 上单独验证字体、DPI、GTK 版本差异；不能用 Linux 截图代替。
- 每个任务后运行 `cargo check --examples`，防止公开签名漂移。

## 15. 完成定义

一个任务只有同时满足以下条件才算完成：

1. 用户可见问题在默认窗口和窄窗口都已复验。
2. 浅色、深色、高对比主题通过。
3. 鼠标与键盘主路径通过。
4. 自动化断言覆盖真实交互层，且做过反向验证。
5. 没有新增 GTK critical、主线程阻塞或整表重画。
6. 文案中英文与占位符通过。
7. 测试隔离配置，证据中无真实秘密。
8. 代码、测试和必要台账分开审查后提交。
9. 若无法完成，明确记录原因、当前行为和后续任务，不用“美化完成”掩盖功能缺口。

本计划全部完成后，PuTTYPlus 的 UI 应从“单页有亮点、关键路径偶发失控”转变为“默认可见、状态明确、错误可恢复、视觉一致的专业桌面工作台”。

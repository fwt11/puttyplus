# 跨平台版构建说明（Windows 优先）

> 阶段 C2 起生效。这份文档讲**怎么把 PuTTYPlus 编到 Windows 上**，
> 以及中途需要的额外工具（Zig）。

## 1. 两个终端引擎

| 引擎 | 用在哪 | 依赖 |
|---|---|---|
| **VTE**（libvte 2.91） | Linux（现有主线，行为零变化） | 系统装 `libvte-2.91-dev` |
| **ghostty-vt**（libghostty-vt 1.0） | Windows（新增后端） | **Zig 0.17.x** 现场编译 |

两个引擎都被封在 `src/termview/` 里，应用层只认 `TermView`
（详见 `src/termview/mod.rs` 顶部的说明）。

## 2. 为什么需要 Zig

libghostty-vt 是 **Zig 写的**（Ghostty 官方源码 tarball）。
crates.io 上的绑定 crate（`ghostty-vt` / `ghostty-vt-sys`）都**不带预编译
静态库**，一律在构建时用 Zig 编译 ⇒ **第一次构建要装 Zig 0.17.x**。

Rust 侧用 `ghostty-vt` 0.8.0（安全封装，FFI 细节由
`src/termview/ghostty.rs` 封死）。

## 3. 装 Zig

### Linux（本机）

放在 `~/.cache/puttyplus-zig/`，**不动系统目录、不改 PATH**，删掉即卸载：

```bash
mkdir -p ~/.cache/puttyplus-zig/bin
# 从 PyPI 的 ziglang wheel 取（官方 Zig 发行版的 Linux x86_64 构建）：
#   https://pypi.org/project/ziglang/
#   ziglang-0.17.1-py3-none-manylinux_2_12_x86_64.whl
# 解压后把里面的 zig 放进 bin/ 即可
~/.cache/puttyplus-zig/bin/zig version   # 应为 0.17.1
```

构建时告诉 cargo 去哪找：

```bash
export ZIG=$HOME/.cache/puttyplus-zig/bin/zig
```

### Windows（CI）

CI 的 `windows-latest` runner 里用官方 tarball 即可
（`https://ziglang.org/download/0.17.1/zig-windows-x86_64-0.17.1.zip`），
解包后把目录加进 `PATH`。

### 3.1 Windows 上到底要装哪些东西？**不需要 MSYS2**

| 用途 | 需要什么 | 要不要 MSYS2 |
|---|---|---|
| **跑 exe**（看效果） | 只需要 GTK4 的 DLL（gvsbuild 的 `C:\gtk\bin\*.dll`） | **不需要** |
| **编译** | Rust（MSVC 工具链）+ Visual Studio 的 C++ 生成工具 + GTK4 预编译包（gvsbuild）+ Zig 0.17 | **不需要** |
| **跑 73 条契约** | 一个 `bash` ⇒ **Git for Windows 自带的 Git Bash 就够**（CI 就是用它） | **不需要**（MSYS2 的 bash 也行，但见下） |

⚠️ **不需要装 MSYS2**：MSYS2 是另一套 MSYS2 环境（自己的 pacman、自己的
运行时），装它只会多一份「PATH 里到底是谁在前面」的麻烦。

⚠️ **但 Git Bash 本身就是 MSYS 系的** ⇒ 它自带那个「参数路径自动转换」的
毛病（`/dev/ttyUSB0` → `C:/Program Files/Git/dev/ttyUSB0`）⇒ 契约脚本在
Windows 上会自己关掉它（见 §9.1 第 2 条）。

> ⭐ **想在 Windows 上直接开发（而不是每轮等 CI 打包）** ⇒ 见
> **`docs/Windows-开发环境搭建.md`**：逐条命令 + 一键脚本
> （`tools\win_setup.ps1`）+ 环境变量持久化（`tools\win_env.ps1`）。
> 装完就能在 Windows 上直接 `cargo build` / `cargo test --lib` /
> `cargo run --example`（**有桌面会话 ⇒ GUI 冒烟能真跑**）。


## 4. 编译

### Linux（默认，**不需要 Zig**）

```bash
cargo build --release
```

`ghostty` 特性默认**关闭** ⇒ 日常构建、CI 的 Linux job 都不碰 Zig。

### 打开 ghostty 引擎（Linux 上也能编）

```bash
ZIG=$HOME/.cache/puttyplus-zig/bin/zig cargo build --features ghostty
```

内核冒烟：

```bash
ZIG=$HOME/.cache/puttyplus-zig/bin/zig cargo run --example ghostty_vt_smoke --features ghostty
```

### Windows

```bash
cargo build --release --target x86_64-pc-windows-msvc --features ghostty
```

⚠️ **MSVC 静态链接的坑**：`ghostty-vt-sys` 在 Windows 上产出的是
`ghostty-vt-static.lib`（静态库），**不是** `ghostty-vt.lib`
（后者是 DLL 的导入库，链错了会得到一堆找不到符号的链接错误）。
crate 的 build.rs 已经按目标平台选对了名字，别手改。

⚠️ 目标三元组 `x86_64-pc-windows-msvc` 需要装 Rust 的 MSVC 工具链
（`rustup target add x86_64-pc-windows-msvc`）与 Visual Studio 的
C++ 生成工具。

⚠️ **路径太长（MAX_PATH 260）时把 target 目录挪到短路径**：

```powershell
$env:CARGO_TARGET_DIR = "D:/t"      # 写成正斜杠（Git Bash 里更稳）
cargo build --release --target x86_64-pc-windows-msvc --features ghostty
```

⇒ 默认的 `target\…` 加上 ghostty 的 `OUT_DIR/src` 与 Zig 的输出目录，
路径轻易超 260 ⇒ 解压、编译、链接都可能失败（报错还很怪）。
⚠️ 挪了之后 **`tools\win_smoke.ps1` 与 `tools\cli_contract_check.sh`
都会认这个环境变量** ⇒ 两边指向同一个二进制，不用手改路径。

## 5. 终端后端怎么选

| 平台 | 默认后端 | 怎么强制 |
|---|---|---|
| Linux | **VTE**（主线，行为零变化） | `PP_TERM_BACKEND=ghostty` 强制用 ghostty（自测用） |
| Windows | **ghostty**（自绘，没有 VTE 可用） | 无需设置 |

Linux 上强制切到 ghostty 的效果（冒烟就是这么跑的）：

```bash
PP_TERM_BACKEND=ghostty xvfb-run -a cargo run --features ghostty --example term_reconnect_smoke
```

⚠️ 这个环境变量是 `TermPane::new` **读**的（不是进程启动时读）⇒
在程序里 `set_var` 也来得及。

### 5.1 终端画面的实现（Windows 版）

Windows 上没有 VTE ⇒ 终端是**自己画的**：`gtk::DrawingArea` + cairo + pango
（`src/termview/ghostty_view.rs`）。

### 5.1 画字：必须走 pangocairo

⚠️ **cairo 的「玩具文字」接口只认 ASCII** —— `cairo_show_text` 遇到中文
会画成一串问号。

正解是 **pango 排版 + pangocairo 落笔**（`pango_cairo_show_layout`）：
字体回退、中文、emoji 全对。

⚠️ **gtk4-rs 没有绑 pangocairo** ⇒ `src/termview/ghostty_view.rs` 里自己
extern 三个函数。两个坑：

1. **参数顺序是 `(cairo_t*, PangoLayout*)`——cairo 在前！**
   写成 `(PangoContext*, PangoLayout*)` 会让 cairo 拿着 PangoContext 的
   指针去建 surface ⇒ 直接 abort
   （症状：`cairo-surface.c: _cairo_surface_create_in_error`）。
2. **别用 GTK 给的 `widget.pango_context()`**：那是 Fc font map 的
   context，和 pangocairo 混用会炸。正解是**自己用
   `pango_cairo_font_map_get_default()` 建一个 context**。

### 5.2 网格对齐

- 单元格尺寸按字体量（`M` 的宽度 = 一列，两行的行高 = 一行）。
- **宽字符（中文）占 2 列**，它的「尾巴格」（`CellWide::SpacerTail`）
  既不画也不占列——画了会多出一个空格，后面的字全歪。
- 空格单元格**没有 grapheme** ⇒ 拼字符串时要补空格，否则行首缩进会丢。

### 5.3 输入法（中文输入）

⚠️ **GTK4 的 `WidgetExt` 没有 `set_im_context`**（GTK3 有）⇒ 自绘控件
要自己挂：

1. `im.set_client_widget(Some(&area))`（GTK4 里是 `set_client_widget`，
   `set_client_window` 已经没了）；
2. 焦点进出时 `im.focus_in()` / `im.focus_out()`；
3. 按键先给输入法 `im.filter_keypress(event)`，**它吃掉了就别再当普通按键
   处理**（否则预编辑时会打出重复的字符）。

commit 之后按 UTF-8 字节发出去（冒烟里有断言）。

## 6. PTY：Linux 的 forkpty 与 Windows 的 ConPTY

| 平台 | 实现 | 在哪 |
|---|---|---|
| Linux | `forkpty`（VTE 自带的 `vte::Pty`） | `src/platform/pty.rs` |
| Windows | **ConPTY**（`CreatePseudoConsole`） | `src/platform/conpty.rs` |

### 6.1 「谁读 master」是两个后端两种做法

- **VTE 后端**：VTE 自己读 master（`set_pty` 之后）⇒ **不要**再起读线程
  （两边抢着读，输出会被撕成两半）。
- **ghostty 后端**：ghostty 只解析字节、**不碰 PTY** ⇒ 由
  `PtySession::spawn_reader` 起线程读，再喂给内核。

⚠️ **pty 的 master fd 是非阻塞的**（VTE 建 pty 时就这么设的）⇒ 直接
`read` 会立刻返回 **EAGAIN**，一个字节都读不到。必须先 `poll` 等有
数据再读。

### 6.2 PTY 的窗口大小要跟终端同步

远端 ssh 靠 pty 的窗口大小知道屏幕多大 ⇒ 不同步的话，远端会一直按
80×24 排版（画面看着正常，其实全错位）。
`examples/ghostty_session_smoke.rs` 就是用远端 `stty size` 断言这件事。

### 6.3 ConPTY 的坑（都写在 `src/platform/conpty.rs` 的文件头）

1. `CreatePseudoConsole` 的两个管道句柄方向：第一个**读端**、第二个**写端**
   （传反 ⇒ 子进程收不到按键）。
2. 传给 ConPTY 的那两个句柄，**创建完必须马上在父进程这边关掉** ⇒
   否则输出管道的写端一直有人握着 ⇒ **读端永远等不到 EOF**（读循环挂死）。
3. `UpdateProcThreadAttribute` 的 `lpValue` 是「**指向 HPCON 的指针**」，
   不是 HPCON 本身 ⇒ 传错 ⇒ 进程能起来但**没挂在伪终端上**。
4. `CreateProcessW` 的命令行是**一整条 UTF-16 字符串**（不是 argv 数组）。
5. **不要设 `STARTF_USESTDHANDLES`** ⇒ 伪终端属性会自动接上三个标准句柄。

### 6.4 ⚠️ Windows 的构建**不能在 Linux 上交叉编译**

`glib-sys`（GTK4 的绑定）在交叉编译时需要 **Windows sysroot 与
pkg-config 的 cross 配置** ⇒ 从 Linux 交叉编译整个程序会卡在 glib-sys。

⇒ **Windows 版只能在 Windows 上编**（CI 的 `windows-latest` 或你自己的
Windows 机器）。能在 Linux 上做的只有「不依赖 GTK 的那部分代码」的交叉
检查（例如 `src/platform/conpty.rs` 单独放一个 crate 用
`cargo check --target x86_64-pc-windows-msvc` 过一遍）。

### 6.5 Linux 上怎么提前发现 Windows 的编译错误

上面那条「只能等 CI」的办法已经固化成脚本了：

```bash
bash tools/win_cross_check.sh
```

它把**不依赖 GTK 的那部分平台层**（`src/platform/localpath.rs` 的本地路径
语义、`src/platform/perm.rs` 的 POSIX 权限 Windows 折算）放进一个临时隔离
crate，跑 `cargo check --target x86_64-pc-windows-msvc` ⇒ **几秒出结果**。

⚠️ **没装那个 target 就提示你装，不自动装**（往机器上装东西要先问用户）：

```bash
rustup target add x86_64-pc-windows-msvc
```

⚠️ **不覆盖**依赖 GTK/GIO 的那部分（clipboard / notify / exe / paths /
ghostty_view…）⇒ 那些只能靠 CI（`.github/workflows/ci-windows.yml`）。

## 7. 已知限制（首版范围）

- **Windows 首版只有**：终端会话 + SFTP 文件面板 + 命令行契约。
  ⚠️ **2026-11-10 起这条扩大了**：端口映射与数据库工作台**在 Windows 上
  也开放**了（见 §11.3.1 与下面「数据库工作台」一条）。
- **数据库工作台**：**Windows 上已开放**（2026-11-10）。它的 GTK 那层
  **零平台分支**，后端也早有 Windows 分支（PostgreSQL 改走回环 TCP 桥）。
  ⚠️ **一处部署侧的差别**：Unix 上 PostgreSQL 走**本地套接字**（远端
  `pg_hba.conf` 多半是 peer/trust，**不校验密码**），Windows 上没有套接字
  ⇒ 走 `127.0.0.1` 回环 TCP ⇒ **远端 `pg_hba.conf` 必须放行 TCP + 密码
  认证**（`host all all 127.0.0.1/32 md5` 之类）⇒ 服务器没配好的话连不上。
  ⇒ MySQL 两边都是回环 TCP，没有这个差别。
- **桌面通知**：Windows 首版不做（状态栏兜底已存在）。
- **中文输入（IME）**：阶段 C3 单独验收——自绘控件要自己挂
  `gtk::IMMulticontext`，兜底方案是隐藏 `gtk::Text` 代理。
- **命令行契约**：含 `/home/<ME>` 路径的用例在 Windows 上做
  **归一化**（基准真值不动）。

## 8. SFTP 面板：两种路径，两套语义（阶段 C5）

⚠️ **这是 Windows 上最容易踩的一类坑**，单开一节说。

### 8.1 远端路径 vs 本地路径

| | 远端（SFTP 那一侧） | 本地（本机文件系统） |
|---|---|---|
| 形状 | 恒为 POSIX：`/srv/data/a.txt` | Linux `/tmp/a.txt`；**Windows `C:\dir\a.txt`** |
| 分隔符 | 恒为 `/` | 平台原生（Windows 是 `\`） |
| 取父目录 | `util::path_parent` | **`platform::localpath::parent`** |
| 拼接 | `util::path_join` | **`platform::localpath::join`** |
| 取文件名 | `util::path_basename` | **`platform::localpath::basename`** |

⇒ **远端那边一律用 `crate::util::path_*`，本地一律用
`crate::platform::localpath::*`，不要混用。**

以前两边共用 POSIX 版，在 Windows 上会出四个错（都已修）：

1. 本地面板「上级」直接跳到文件系统根（POSIX 找不到 `/`）；
2. 本地文件重命名对话框预填的是**完整路径**（basename 拿不到名字）；
3. **上传后远端出现一个叫 `C:\dir\a.txt` 的文件**（远端目标名取自本地路径）；
4. 本地重命名落到「进程当前工作目录」而不是面板当前目录（老 bug，Linux 上也有）。

### 8.2 `file://` URI（拖放上传 / 剪贴板粘贴上传）

`text/uri-list` 里的路径是 **URI**，不是本地路径：

- 生成：手搓 `format!("file://{p}")` 在 Windows 上得到
  `file://C:\dir\a.txt`（反斜杠 + 少一个斜杠）⇒ 源端与目标端都认不出。
  ⇒ 用 `platform::localpath::to_file_uri`（GIO 负责百分号编码与盘符）。
- 解析：以前只认「以 `/` 开头」的路径 ⇒ **Windows 的 `C:\…` 全被丢掉**
  （拖放上传与剪贴板粘贴上传直接失效）。
  ⇒ 用 `platform::localpath::from_file_uri` 解析 +
  `platform::localpath::is_abs` 判定（Windows 上认盘符与 UNC）。

## 9. 命令行契约检查怎么跨平台跑（阶段 C5）

`tools/cli_contract_check.sh` **在 Windows（Git Bash）上也能跑**，对照的还是
同一批 73 条黄金基准（基准真值不动）。

三处平台差异在脚本里被**归一化**掉：

1. **home 目录的形状**：Linux 是 `/home/<user>`，Windows（Git Bash）的 `~`
   展开成 **MSYS 风格**的 `/c/Users/<user>`（不是 `C:\Users\<user>`！），
   原生形式还有 `C:/Users/<user>`。
   ⇒ 脚本把这些形态统一替换成 `/home/<ME>`。
2. **反斜杠**：Windows 路径里的 `\` 先转成 `/`。
3. **默认用户名**：Windows 上没有 `id -un` 的可移植替代 ⇒ 依次取
   `id -un` → `%USERNAME%` → `%USER%` → `%USERPROFILE%` 的末段。

⚠️ **fixture HOME 按平台给不同变量**：Unix 走 `HOME`，Windows 走
`USERPROFILE`（GLib 的 `g_get_home_dir()` 在 Windows 上读的是它；而且
MSYS 的 `HOME` 是 MSYS 风格路径，原生程序拿它是错的）。

```bash
bash tools/cli_contract_check.sh --selftest   # 只测归一化逻辑（喂假形态）
bash tools/cli_contract_check.sh              # 对照 73 条基准
```

⚠️ `--selftest` 的用处：Windows 上 73 条全 DIFF 有两种可能——「程序行为变了」
或「归一化坏了」。先跑自测能立刻分清。

### 9.1 Windows 上跑契约的**三个坑**（阶段 C6，第 12 轮 CI 实测）

第 12 轮 Windows CI：单测全绿，契约从「73 条全 DIFF」降到 **8 条 DIFF** ⇒
根因全在**环境/测试侧**，不在程序：

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | `sw_T` / `ignored_A` / `val_L` 读到**别的用例**的输出 | **Windows 文件系统大小写不敏感** ⇒ `sw_t.txt` 与 `sw_T.txt` **互相覆盖** | 三对撞名的用例改名加 `_lower` / `_upper` 后缀（基准文件同步重命名，**内容一字未改**） |
| 2 | `proto_serial` / `val_i` 的路径变成 `C:/Program Files/Git/dev/ttyUSB0` | **Git Bash（MSYS 系）自动把 `/xxx` 参数转成 Windows 路径** | 脚本在 Windows 下 `export MSYS_NO_PATHCONV=1` + `MSYS2_ARG_CONV_EXCL='*'` |
| 3 | `sshconfig_alias` 没展开成 `10.1.1.1` | 会话 fixture 叫 `Demo`、别名叫 `demo` ⇒ **只差大小写** ⇒ Windows 上 `demo` **命中了 PuTTY 会话** ⇒ 别名展开根本没跑 | 别名用例用**单独的 fixture home**（只有 `.ssh/config`，没有 `.putty`）⇒ 两个平台行为一致 |

⚠️ **第 3 条不是程序的行为差异**：C 版（`c/src/args.c:338`）与 Rust 版
（`src/args.rs` 位置参数分支）都是**「会话优先」**，在 Windows 上同样会命中
大小写不敏感的文件 ⇒ 差的是**测试环境** ⇒ 修在测试侧，**基准一个字没改**。

⇒ 这三条都进了 `--selftest`：**少一个变量 / 基准名撞车 ⇒ 自测立刻报错**，
不用等 73 条里挂几条才反应过来。

## 10. Windows 真机验证清单

⚠️ **Windows 版没在 Linux 上交叉编译过**（`glib-sys` 要 Windows sysroot）⇒
只能真机 / CI 上验。GitHub 的 `windows-latest` runner **没有桌面会话**
⇒ CI 只能做「编译 + 单测 + 命令行契约」，**GUI 那一半要人来跑**。

⇒ 在自己的 Windows 机器上，一条命令能把「编译 + 契约」都跑完：

```powershell
powershell -ExecutionPolicy Bypass -File tools\win_build.ps1
```

⇒ 编译完再跑一遍**自动**冒烟（能自动验的那部分：exe 起不来不崩、参数抽查、
73 条契约）：

```powershell
powershell -ExecutionPolicy Bypass -File tools\win_smoke.ps1
```

### 10.1 两条拿到 exe 的路

| 路线 | 怎么做 | 适合什么时候 |
|---|---|---|
| **A0. 从 Release 下** | Releases 页 → 最新的版本 → 资产里的 **`puttyplus-windows-x86_64.zip`** ⇒ 解压后双击 `puttyplus.exe` | **最省事**（不用等 CI）。⚠️ 0.5.0 发布时**还没有**这个资产（发布流程当时只编 Linux）⇒ 从 **0.5.1** 起才有 |

## 11. Windows 版的终端：进程内 SSH（阶段 C7）

### 11.1 为什么不用外部程序

Windows 上默认**没有 `ssh.exe`**（OpenSSH 是「可选功能」，很多机器根本没装），
`plink` 又是 PuTTY 的东西、**我们不打算依赖** ⇒ 走「spawn 一个 ssh 子进程」
那条老路必然失败（用户 2026-11-08 报的「找不到可用的客户端程序」）。

⇒ **自己实现 SSH 客户端**：用 russh（本来就是依赖——SFTP 面板那条链路就是它）
在**进程内**说 SSH。

### 11.2 怎么跑的

```
键盘字节 ──► ShellChannel（SSH channel）──► 远程端
远程端字节 ──► ShellChannel ──► ghostty 内核 ──► 自绘画面
窗口尺寸 ──► SSH 的 window-change ──► 远程端（远端据此排版）
```

- **不需要本地 pty** ⇒ 没有本地回显、没有本地行规程、没有「等 ssh 切 raw
  模式」那一套（这是比「自己编一个 ssh.exe 子进程」好的地方）。
- 认证走**与 SFTP 面板同一段代码**（`backend::conn::connect_session`）⇒
  密码 / 指定私钥 / agent / 默认私钥的顺序与行为两边一致。
- 认证失败且没有凭据 ⇒ **弹框问密码**再重试（与 SFTP 面板同一套）。

### 11.3 与 Linux 主线的差异（**Linux 不变**）

| | Linux 主线 | Windows |
|---|---|---|
| SSH 从哪来 | **spawn 用户自己的 `ssh`** | **进程内 russh** |
| `~/.ssh/config` | 全都生效（别名、ProxyJump、IdentityFile…） | ⚠️ **不读**（别名展开由本程序自己做：HostName/Port/User/IdentityFile 生效；**ProxyJump 不支持**） |
| agent | 用 ssh 自己的 | **用 russh 自己的**（阶段 C10：**已实现**——Windows 的 agent 在命名管道 `\\.\pipe\openssh-ssh-agent` 上，OpenSSH for Windows 与 Git for Windows 通用 ⇒ 密钥在 agent 里时**免密**，与 Linux 一致） |
| 端口转发 | `ssh -L/-R/-D` | 本程序自己的**进程内转发**（三类 `-L`/`-R`/`-D` 都支持，走 `direct-tcpip` 通道） |

⚠️ **Linux 主线保持 spawn 是刻意的**（AGENTS.md 的零回归红线）：终端里跑的
是用户自己的 ssh ⇒ 他的 `~/.ssh/config`、agent、ProxyJump、known_hosts
的行为**原样保留**。Windows 版做不到这个 ⇒ 上面这些是**已知差异**。

### 11.3.1 端口转发由谁承接：**看终端用哪条路，不是看系统里有没有 ssh`

转发有**两套机制**：

| 机制 | 谁在跑 | 怎么实现 |
|---|---|---|
| **argv 承接** | 终端 spawn 的 `ssh`/`plink` | 它们自己处理 `-L/-R/-D` |
| **进程内引擎** | 本程序 | 自己开 `direct-tcpip` 通道（`backend/forward.rs`，三类都支持） |

⇒ **判据是「终端用哪条路连」**（`term::use_inproc_ssh()`）：

- 终端走 **spawn**（Linux 主线）⇒ 转发进 ssh 的 argv；
- 终端走 **inproc**（Windows 默认）⇒ 终端**根本没有** ssh 进程 ⇒ 命令行的
  `-L/-R/-D` 交给**进程内引擎**承接。

⚠️ **这里原先有个坑**（2026-11-10 填掉）：旧判据是「系统里找得到
`ssh`/`plink` 就当转发归它管」⇒ Windows 机器上**只要装了 OpenSSH**
（Win10/11 的可选功能，很多人装了），转发就被判给了一个**根本不会被启动**
的 ssh ⇒ **转发静默失效、界面上一点提示都没有**。
⚠️ 同一个坑在 Linux 上也有：`PP_TERM_SSH=inproc` 时终端不 spawn ssh，转发
却被判给了 ssh ⇒ 一样失效。现在两边统一看 `use_inproc_ssh()`。

⚠️ **语义差异**：进程内转发生效在**本程序自己那条 SSH 连接**上（跟 SFTP
面板同一条）⇒ 它随那条连接生死，不随终端页签生死。

### 11.4 怎么验（Linux 上就能验）

```bash
ZIG=~/.cache/puttyplus-zig/bin/zig xvfb-run -a \
  cargo run --features ghostty --example ssh_shell_smoke
```

它验四件事：连上本地 sshd ⇒ 命令输出上屏 ⇒ **远程端 `stty size` 与终端
一致**（= window-change 生效）⇒ 中文 UTF-8 字节过去。

**端口映射**也有一个 Linux 上就能跑的冒烟（它走的就是 Windows 上那条路）：

```bash
PP_TERM_SSH=inproc xvfb-run -a cargo run --example fwd_inproc_smoke
```

它起一个本地回显服务当转发终点 ⇒ 用带 `-L` 的会话连本机测试 sshd ⇒ 等
转发端口起来 ⇒ **通过转发端口发一串字，看它是不是原样回来**（不是"端口在
监听但不通"）。⚠️ 必须带 `PP_TERM_SSH=inproc`：Linux 上默认走 spawn ⇒
转发归 ssh 的 argv，不走进程内这条。

⚠️ **进程内 SSH 只有 ghostty 后端能用**（VTE 的输入必须过一个本地 pty）⇒
Linux 上要自测这条通路，得配 `PP_TERM_BACKEND=ghostty`（那个冒烟自己会设）。
⇒ 环境变量 `PP_TERM_SSH=inproc|spawn` 可强制切换（Windows 上默认 inproc）。


## 12. 密码：**两个平台是同一套**（阶段 C9）

### 12.1 为什么要专门做这一层

用户 2026-11-08 在 Windows 上报「SFTP 和终端要分别输密码，分屏也要输」，
随后又指出「Linux 版和 Windows 版看起来完全像两个东西」。
⇒ 查下来，**代码本来就是共享的**（`src/` 里 85000+ 行，平台相关的
`cfg` 只有 96 行 ⇒ 99.9% 是同一份代码；差异集中在 `src/platform/` 与
终端后端），但**产品的行为**在密码这一块分叉了：

| | Linux 主线 | Windows（改动前） |
|---|---|---|
| SFTP 面板问密码 | 我们的对话框 | 我们的对话框 |
| 终端问密码 | **spawn 出去的 `ssh` 在 tty 上自己问** | 我们的对话框（进程内 SSH） |
| 分屏终端 | 又一条 ssh ⇒ 又问一次 | 又一条连接 ⇒ 又问一次 |

⇒ 同一个会话要输 2～3 次密码，**而且两个平台的问法不一样**。

### 12.2 现在怎么统一

新增 `src/pwcache.rs`：**「密码从哪来」是共享的一层**，两个平台共用：

1. **进程内缓存**（`pwcache::get/put`）：按 **(host, port, user)** 认人 ——
   谁先连上、谁问的密码，后面的连接直接拿来用。
2. **密码框去重**（`pwcache::ask_once`）：同一条会话**只弹一个框**，
   后到的连接挂进等待队列，框里一有答案大家一起走。
3. **会话级密码文件**（`pwcache::write_session_file` /
   `read_session_file_wait`）：**给 spawn 出去的 `ssh` 用的**。
   Linux 主线的终端跑的是**用户自己的 ssh**（零回归红线）⇒ 认证是那个
   进程自己做的 ⇒ 我们**看不到**它的提问 ⇒ 改让 ssh 问**我们**：

   ```
   ssh（spawn 出去的）
     │  SSH_ASKPASS=<本程序> + SSH_ASKPASS_REQUIRE=force（OpenSSH ≥ 8.4）
     ▼
   askpass 助手（= 本程序的另一个进程）
     │  等「会话级密码文件」出现 → 读出来 → 打印给 ssh → 把文件清空
     ▼
   父进程（SFTP 面板的对话框）：把密码写进那个文件
   ```

⇒ **两个平台现在都是「我们的对话框问一次」**：终端、SFTP、分屏共用同一份
密码。

⚠️ **Linux 主线有一处用户可见的变化**：终端里 `ssh` 的密码提示**不再在
tty 上出现**（改成我们的对话框）。这是**故意的**——原来那个提示在终端里，
SFTP 的提示在对话框里，两处不一样。**要密码的场景**（堡垒机 launcher 传
`-pw`）**完全不受影响**：那时密码早就有 ⇒ 走 `PUTTYPLUS_PW` 直接应答，
连框都不弹。

⚠️ **读完要把会话文件清空**（不是删掉）：密码不留盘；而 **ssh 密码错时
会重试 3 次** ⇒ 每次都调一次助手 ⇒ 要是把文件删掉，第 2、3 次就会干等到
超时（终端像卡住）⇒ 清空之后，重试读到的是空串 ⇒ 立刻失败、不卡。

### 12.3 怎么验

```bash
# ① 单元测试（密码缓存 / 密码框去重 / 会话文件通气 / askpass 助手）
cargo test --lib pwcache::
cargo test --lib term::tests::askpass

# ② 真 e2e：spawn 出去的 ssh 真的去问我们的助手
BIN=$(pwd)/target/debug/puttyplus
printf 'secret-pw' > /tmp/pp_pwtest.tmp
SSH_ASKPASS=$BIN SSH_ASKPASS_REQUIRE=force PUTTYPLUS_PW_FILE=/tmp/pp_pwtest.tmp \
  ssh -p 2234 -o UserKnownHostsFile=/dev/null -o StrictHostKeyChecking=no \
      -o NumberOfPasswordPrompts=1 -o PreferredAuthentications=password \
      ops@127.0.0.1 true
cat /tmp/pp_pwtest.tmp     # ⇒ 空 ⇒ 助手被调用了，密码取走了
```

（`2234` 那个 sshd 是本地测试用的：`PasswordAuthentication yes`。
仓库里默认的 `2233` 只开 publickey ⇒ ssh 压根不会问密码 ⇒ 验不了。）

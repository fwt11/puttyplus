### 3.1 最值得肯定的地方

1. **编辑器是当前设计标杆。** 页签同时表达位置与模式，工具栏、路径、语法高亮、查找条和状态栏职责清楚，没有把工具堆成按钮墙。
2. **数据库数据页专业。** 列头类型、WHERE 与本地筛选的区分、执行工具条、SQL 区和底部状态信息形成了可信的工作台层级。
3. **Docker 文件页完成度高。** 图标、权限原文、路径、`..`、资源列与操作列清楚；真实目录导航可用。
4. **组件语言正在收敛。** 药丸、状态点、图标按钮、tooltip、主题令牌和组件画廊为后续统一提供了良好底座。
5. **安全交互意识好。** 目录镜像默认不删除且二次确认；破坏性操作有明确后果说明。
6. **不是“换皮”就能解决。** 现有风格适合基础设施工具，应该保留专业、紧凑、低装饰的方向。

## 4. P0：必须优先修复

## P0-1 Docker 列表在默认窗口宽度下溢出，操作列跑出可视区

**状态：已确认**  
**影响：核心操作不可见；资源列贴边；横向信息被裁切**  
**证据基线：2026-11-25 `e223ccd`；相关列宽代码在 `e51cfd1` 未变化**

![Docker 默认窗口下列表溢出](file:///tmp/pp-ui-audit-fresh-20261125/shots/08-docker-list.png)

### 现象

应用按默认 `1200 × 780` 创建窗口，左侧会话树再占去一部分宽度。Docker 列表中可以看清名称、ID、镜像、端口和状态，但：

- 右侧资源列只剩局部；
- “操作”列不在可视区内；
- 用户第一眼无法找到启动、停止、重启、详情等入口。

截图中的黑边来自 Xvfb 根窗口比应用窗口大，不是产品问题；被裁切的资源列和缺失的操作列是实际应用窗口几何的结果。

### 根因

六列都设置了较大的最小宽度，且镜像、端口、状态、资源四列同时扩展：

| 列 | 最小宽度 | 是否扩展 |
|---|---:|---|
| 名称 | 200 | 否 |
| ID | 84 | 否 |
| 镜像 | 240 | 是 |
| 端口 | 180 | 是 |
| 状态 | 125 | 是 |
| 资源 | 190 | 是 |

操作列不扩展，但固定为 `24px × 4 + 24px = 120px`。六列最小宽合计 **1019px**，加操作列约 **1139px**，还没有计算列间距、内边距、边框、滚动条和侧栏。

默认主窗为 `1200 × 780`，侧栏最小宽度为 `180px`；内容区通常不足 1000px。因此最小宽度需求超过实际可用宽度，TreeView 只能把右侧内容推到可视区外。

源码：

- [src/main.rs:139](file:///home/fwt/workspace/projects/putty/src/main.rs#L139) 默认窗口尺寸
- [src/main.rs:154](file:///home/fwt/workspace/projects/putty/src/main.rs#L154) 侧栏最小宽度
- [src/panel/dockerui.rs:2895](file:///home/fwt/workspace/projects/putty/src/panel/dockerui.rs#L2896) 六列宽度策略
- [src/panel/dockerui.rs:2956](file:///home/fwt/workspace/projects/putty/src/panel/dockerui.rs#L2956) 操作列宽度

### 影响

- 用户不知道核心操作在哪里，容易认为功能缺失；
- 必须拖宽窗口或拖侧栏才能使用，增加操作成本；
- 资源列在右缘被裁切，状态信息不完整；
- 默认体验与“宽屏截图”不一致，首次使用可信度下降。

### 修复建议

不要只把窗口默认宽度调大，应该同时做三件事：

1. **建立列优先级。**
   - 必显：名称、状态、操作；
   - 次显：镜像、端口；
   - 可折叠：资源。
2. **按可用宽度切换布局。**
   - 宽窗口：显示完整六列；
   - 中等宽度：资源并入状态或 tooltip；
   - 窄窗口：隐藏 ID 或镜像，保留名称、状态、操作。
3. **降低最小宽度总和。**
   - 名称、镜像、端口按内容设置更小的下限；
   - 只让一到两列吸收富余，避免四列同时扩展；
   - 操作列保持紧凑，但必须始终可达。
4. **让状态和资源有清晰的降级方式。** 隐藏列不等于丢信息，hover、详情弹窗和列设置应能补回。

### 验收标准

- [ ] 默认 `1200 × 780`、侧栏默认宽度下，操作列完整可见；
- [ ] `1024 × 700` 下名称、状态、操作仍可见；
- [ ] 任意宽度下不需要横向滚动才能执行启停、重启和查看详情；
- [ ] 宽窗口不出现大片空谷；
- [ ] 列隐藏后，完整信息仍能在详情或 tooltip 获取；
- [ ] 使用真实 `path_at_pos` 坐标点击每颗图标，动作与图标一致；
- [ ] 冒烟覆盖默认窗口与窄窗口两种几何，不只检查模型列数。

## P0-2 主按钮实际文字对比度不达 WCAG AA，深色错误色也不足

**状态：已确认**  
**影响：按钮文字可读性不足；高对比主题之外仍有可访问性缺口**  
**证据基线：源码与颜色计算，2026-11-26 `e51cfd1`**

![组件画廊浅色主题](file:///tmp/pp-ui-audit-current-20261126/auto/pp-gallery-light.png)

### 现象

主按钮使用蓝底，但内部文字并不是预期的白色，而是接近深色正文色。浅色主题中形成“蓝底深字”，与普通按钮的视觉区分度也不够理想。

这不是单纯审美问题。按实际计算：

| 场景 | 实际对比度 | AA 普通文字 |
|---|---:|---|
| 浅色 `.pp-primary`：深字 on 蓝底 | **3.24:1** | 不达标 |
| 深色 `.pp-primary`：浅字 on 蓝底 | **3.08:1** | 不达标 |
| 浅色主按钮若改为白字 | 4.88:1 | 达标 |
| 深色主按钮若改为白字 | **4.12:1** | 仍不达标 |
| 深色危险按钮白字 | **3.96:1** | 不达标 |
| 浅色危险按钮白字 | 5.44:1 | 达标 |
| 浅色正文 on panel | 15.80:1 | 达标 |
| 浅色 dim on panel | 6.09:1 | 达标 |
| 深色正文 on panel | 12.11:1 | 达标 |
| 深色 dim on panel | 6.13:1 | 达标 |

正文与次级文字是达标的，问题集中在**强调色按钮**。

### 根因

主题中有一条覆盖 `label` 的通用颜色规则：

```css
label, button, entry, checkbutton, radiobutton, treeview, textview,
menubar, notebook, treeview.view {
  color: @pp_fg;
}
```

GTK4 按钮里的文字是独立的 `label` 节点。`.pp-primary` 虽然给按钮容器设置了 `color: @pp_on_accent`，但内部 Label 被上面的显式规则覆盖。

现有规则只显式处理了：

```css
button.pp-primary image { color: @pp_on_accent; }
```

没有对应的：

```css
button.pp-primary label { color: @pp_on_accent; }
```

此外，深色主题的 `pp_accent = #3d7dd6` 与 `pp_err = #d9534f` 即使搭配白字，对比度仍低于 4.5:1。

源码：

- [src/theme.rs:1471](file:///home/fwt/workspace/projects/putty/src/theme.rs#L1471) 通用文字颜色
- [src/theme.rs:1576](file:///home/fwt/workspace/projects/putty/src/theme.rs#L1576) 主按钮样式
- [src/theme.rs:1591](file:///home/fwt/workspace/projects/putty/src/theme.rs#L1591) 只处理了图标
- [src/theme.rs:1775](file:///home/fwt/workspace/projects/putty/src/theme.rs#L1775) 深色令牌
- [src/theme.rs:1797](file:///home/fwt/workspace/projects/putty/src/theme.rs#L1797) 浅色令牌

### 影响

- 主按钮文字在浅色与深色主题下都不够清楚；
- 深色主题的危险操作辨识度不足；
- 低视力用户、强环境光和老旧显示器受影响更明显；
- “主操作更醒目”的目标被低对比度抵消。

### 修复建议

1. 为主按钮 Label 增加显式颜色规则，并覆盖 disabled / hover / active 状态。
2. 不要只修 `.pp-primary`，要建立“实心按钮内部文字”的统一规则，并检查 `suggested-action`、`destructive-action` 及自定义实心按钮。
3. 调整深色主题强调色和错误色，使白字达到 4.5:1；保持色相不变，优先加深背景。
4. 将对比度计算加入单元测试或构建期检查，避免以后改令牌时静默退化。
5. 三主题都验，不能只验浅色。

### 验收标准

- [ ] 三套主题下，主按钮、危险按钮普通状态文字对比度均 ≥ 4.5:1；
- [ ] hover、active、disabled 仍有明确状态差异；
- [ ] 图标与文字颜色一致；
- [ ] 高对比主题不被普通主题规则覆盖；
- [ ] 用真实 GTK 样式上下文读取计算后的颜色，而不是只检查 CSS 字符串；
- [ ] 新增令牌时有自动对比度回归测试。

## P1-1 连接管理器、认证、转发和设置窗口“上密下空”

**状态：已确认**  
**影响：窗口效率低；短页签被最高页签撑高；页面显得未完成**  
**证据基线：当前代表性复验 + 全面采样**

![连接管理器浅色主题](file:///tmp/pp-ui-audit-current-20261126/auto/pp-connmgr-light.png)

![设置窗口外观页](file:///tmp/pp-ui-audit-current-20261126/shots/settingsui_shot.png)

### 现象

连接管理器的某些页签表单密集，窗口下部却有相当大的空白；认证、转发等较短页签尤其明显。设置窗口的“外观”页只占上部区域，下部留白很多。

这会让同一个窗口在不同页签之间出现明显的“密度跳变”：用户刚看完紧凑表单，切到短页签后感觉内容消失了。

### 根因

连接管理器让所有页签共享一个由**最高页签**决定高度的 ScrolledWindow：


## 8. 设计系统建议

### 8.1 产品定位

建议把视觉目标定义为：

> **专业、紧凑、可信赖的基础设施工具。**

不是消费级娱乐产品，不需要大标题、强阴影、渐变或过度动效。优势来自：

- 稳定布局；
- 高信息密度；
- 明确状态；
- 可预测操作；
- 克制的颜色。

### 8.2 三种窗口模式

| 模式 | 代表界面 | 结构 |
|---|---|---|
| 工作台 | 主窗口、数据库、Docker | 持久导航 + 工具条 + 内容 + 状态栏 |
| 表单对话框 | 连接管理、认证、转发、新建连接 | 页签 / 分组 + 滚动内容 + 固定底部操作 |
| 工具窗口 | 设置、队列、通知、镜像、快捷键 | 标题栏 + 单一任务 + 明确关闭入口 |

不要用同一种“最高页签撑满窗口”的策略处理所有模式。

### 8.3 间距与尺寸

建议建立以下基础令牌：

| 类别 | 建议值 |
|---|---|
| 间距 | 4 / 8 / 12 / 16 / 24 |
| 控件高度 | 28 / 32 / 36 |
| 卡片内边距 | 16 / 20 |
| 表单行间距 | 8 / 12 |
| 图标尺寸 | 16 / 24 |
| 圆角 | 6 / 8 / 12 |
| 工具条最小高度 | 40 / 44 |

这些值不是要求所有控件一样大，而是要求**同类控件一致、不同层级有明确比例**。

### 8.4 颜色令牌

保留当前令牌结构，但补充用途命名和对比度约束：

- `bg`：应用背景；
- `panel`：主要工作表面；
- `card`：需要浮起的表面；
- `fg` / `dim`：正文与次级文字；
- `accent`：选择、焦点、主操作；
- `on_accent`：实心强调按钮文字；
- `ok` / `warn` / `err`：状态与破坏性操作；
- `border` / `hover` / `selected`：交互边界。

硬性规则：

1. 实心按钮必须同时定义容器色和内部 Label 色；
2. 普通文字对比度 ≥ 4.5:1；
3. 大标题或图标可按 3:1，但要有明确尺寸门槛；
4. 状态不能只靠颜色，必须同时有文字或图标；
5. 三主题共享语义，不共享未经检查的色值。

### 8.5 空态模式

空态统一回答三个问题：

1. 这里为什么是空的？
2. 下一步最重要动作是什么？
3. 如何获得更多信息？

推荐结构：

```text
小图标 / 小品牌标记
一句任务标题（不是产品名重复）
一句解释
主 CTA
可选的次要入口或快捷键
```

品牌卡只适合欢迎页或关于页，不适合数据库、文件、队列等任务工作台。

### 8.6 错误模式

错误提示统一为：

```text
发生了什么（中文分类）
可以做什么（明确动作）
为什么 / 原始详情（tooltip 或展开）
```

不要只把 Docker、SSH、数据库驱动原文塞进 Label，也不要用“操作失败”抹掉所有区别。

## 9. 测试假象、限制与未覆盖项

### 9.1 已识别并排除的假象

| 假象 | 原因 | 处理 |
|---|---|---|
| Xvfb 截图黑边 | 根桌面尺寸大于应用窗口 | 不作为产品缺陷 |
| 约 3.9KB 的全黑 PNG | 示例截屏前已退出，或窗口尚未映射 | 只采用 `auto/` 中有效窗口图 |
| `GtkDialog mapped without a transient parent` | 独立审计窗口缺少真实主窗 | 不直接归因产品主窗口 |
| GTK accessibility bus 警告 | Xvfb 无 a11y 服务 | 视为环境噪音 |
| 数据库空态写“还没有选中数据库连接” | 测试先开页面、后设置连接 | 不作为产品提示缺陷 |
| 数据库 E2E 行数不一致 | 测试把筛选后的 2 行当作全表 3 行基线 | 改用干净只读页面取证 |
| Docker 文件页第一次读不到私钥 | 通用脚本隔离 HOME | 保留真实 HOME 读密钥，隔离 XDG 与配置 |
| 回放黑屏 | 宿主未稳定映射，且存在重复 Separator 断言 | 不把黑屏当视觉结论 |
| 旧截图中的探针对象 | 前一次 E2E 失败残留 | 已清理 `pp_probe_*`，不作为产品数据 |

### 9.2 测试侧问题

部分日志出现 `gtk_css_node_insert_after` critical，但没有对应可见症状。本报告不把它升级为确定 UI 缺陷，只建议后续在干净环境追踪，确认是否存在 CSS 节点顺序问题。

### 9.3 尚未覆盖

- Windows 原生 GTK 后端；
- Wayland；
- 高 DPI 与系统缩放；
- 屏幕阅读器与完整键盘可达性；
- 所有语言状态；
- 真实用户长期使用中的配置恢复；
- 回放完整视觉；
- 镜像真正执行后的结果态；
- 高对比主题的每一个页面。

这些项目不应根据 Linux X11 截图推断“通过”或“失败”。

## 13. 最终结论

PuTTYPlus 已经具备一款专业 SSH / SFTP / 数据库工具的基本盘：功能完整、信息密度高、状态系统初成、编辑器与数据库工作台有明显亮点。当前最需要的不是一次激进重设计，而是一轮**以默认窗口、可访问性、窗口结构和异常状态为核心的收口**。

如果只允许做三件事，建议做：

1. **让 Docker 的核心操作在默认窗口下永远可见；**
2. **修好主按钮与深色错误色的对比度；**
3. **统一表单窗口和空态，让用户始终知道下一步。**

做到这三点，用户对“专业、精致、可信赖”的感受会有明显提升，而且不需要牺牲现有功能密度或改变用户已经熟悉的工作方式。

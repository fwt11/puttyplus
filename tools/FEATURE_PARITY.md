## 有意差异（白名单，均有理由）

| 差异 | 理由 |
|---|---|
| SFTP 每请求 300 秒超时 | russh-sftp 默认 10s 在慢链路+并发预取下必超时（实测 410KB/s 下载 58MB 首包即失败）；libssh 无此机制，300s 为防死锁兜底 |
| 协议层内部错误措辞（握手/密钥交换等） | 分别来自 libssh / russh，网络层 errno 文案已用 strerror 同源对齐（如中文"拒绝连接"） |
| GTK4 在无父窗口对话框场景多一行 stderr Gtk-Message | GTK3 无此提示，纯日志噪音 |

> 2026-10 起采用"Rust 主线开发、C 冻结为兼容基线"策略：CLI/协议行为仍由

| 新建连接对话框的按钮是「连接」（阶段 29） | 所有入口建完都**立刻连上并打开工作台**，按钮写「保存」是**误导**——用户以为存个配置文件就完事了，可堡垒机场景下会话本身都没保存，"保存"既做不到也没意义。成功提示也跟着改：不再弹「连接已保存」（**还没连上**，且弹窗会压在刚打开的工作台上），只在**密码没记住**时弹一句「密码没记住」。⚠️ **照样落盘**：工作台按会话键从 `databases.ini` 列连接（`use_profile` → `dbstore::get`），不落盘这条连接建完就"找不到"、点了「连接」也连不上——落的是**连接定义**（地址/端口/用户/库名，数据库侧的东西），不是 SSH 会话 |

| 凭据库管理器（阶段 31） | 连接管理器底部「凭据库…」按钮打开一个**管理器窗口**：列出**库里有哪些连接名 + 各自属于哪个会话**（`db:<会话键>/<连接名>`，见 `dbstore::split_vault_name`）+ 四个动作（**改主密码 / 重置凭据库 / 锁定 / 关闭**）+ 状态行（已解锁 / 已锁定 / 明文模式）。原先解锁完只提示一句"已解锁"，用户**什么也看不到**。**改主密码**（`vault::change_master`）把凭据一条不少地搬过去，旧密码错则拒绝且文件不动；⚠️ **不许降级成明文**（新密码留空被拒），要降级走「重置」（那里有后果确认）。**空主密码 = 明文模式**：文件格式升到 `version=2` 并在文件头明写 `protected=true\|false`——一眼就能看出这份库**没加密**，而不是看到一堆 base64 就以为它是安全的；⚠️ **不假装加密**（空串派生出的密钥谁都能算出来）；老库（无 `protected` 键）按加密处理。明文模式下解锁直接成功 |
| 「在此处打开终端」（阶段 32） | 远程文件列表右键多一项「在此处打开终端」（`utilities-terminal-symbolic`）；**本地面板不显示**（本程序的终端全是远程 SSH 会话，没有本地 shell）。行为 = 在**当前标签**里**新开一个终端页签**（新 SSH 会话）并 `cd` 到那个目录——⚠️ **不复用当前终端**（当前终端可能正跑着命令，塞 `cd` 会打断用户手上的事）。目标目录由纯函数 `term_target_dir` 决定：右键**目录**进它、右键**文件**进它所在目录、没选进当前目录。`cd` 通过**就绪钩子**下发（`TermPane::set_ready_hook`，ssh 子进程 spawn 成功后才往 pty 写）——写早也不怕，pty 是 pipe，认证通过后才发给远端 shell；⚠️ 钩子传 `&vte::Terminal` 而**不是** `TermPane`（捕获自己 = 自引用环，面板永远释放不掉） |
| 拖拽上传（阶段 32） | 拖文件到**远程文件列表**或**拖到终端**都能开始上传。终端上挂 `gdk::FileList` 的 DropTarget，⚠️ **只接 `text/uri-list`**：VTE 自己的拖放是**拖选文本**（接 String），两者类型不同、互不抢，"从终端往外拖文本到编辑器"的老功能不受影响。目标目录 = **面板当前浏览的远程目录**。⚠️ 顺手修了真 bug：`drag_from`（"程序内拖拽"标记）原来只在 `prepare` 里设**从不重置**——"在程序里拖过一次"之后，再从**文件管理器**拖文件进来会被当成"同面板自拖"**直接拒掉**，用户看到的就是"拖进来没反应"；现在 `connect_drag_end` 里清回 `None`。⚠️ DropTarget 闭包一律抓**弱引用**（抓强引用 = 「PanelState → 控件 → DropTarget → PanelState」的引用环，面板永远释放不掉）。GTK 没有"模拟拖放"的 API，所以上传入口抽成 `panel::drop_upload_files(st, &FileList)`，冒烟调**同一段代码**验证（上传后远端文件确实存在、内容一致） |
| X11 选区直读（阶段 101） | 让**跨进程拖拽**在 GTK4 下真的拿到文件。GDK4 读拖拽数据的唯一入口 `gdk_drop_read_async()` 在 X11 后端是「请求方 = GDK 的隐藏 leader 窗口 + 时间戳 = `CurrentTime`」，而源端（Deepin 文件管理器 = Qt5）要**对上号**才肯供数（`QXcbDrag::handleSelectionRequest()`：时间戳对得上那次拖拽，或请求方就是收到拖放的窗口）⇒ GDK4 那条路四条全落空 ⇒ 源端回 `property=None` ⇒ 一个字节都拿不到。⚠️ **阶段 100 那个「源端不提供数据」的结论是错的**（源端是肯给的，只是挑问法）。修法：drop 回调里自己发一次 `XConvertSelection`，**请求方 = 顶层窗口的 XID**（`gdk_x11_surface_get_xid`；GDK4 把 `XdndAware` 挂在顶层 surface 上）⇒ 命中源端的 `findXdndAwareParent` 分支；源端把数据写进**请求方窗口的属性**，我们**轮询属性**拿数据（不接 `SelectionNotify` 事件——那个事件 GDK 会先读走）。新模块 `src/panel/xdnd11.rs`（libX11 FFI + `gdk_x11_*`）。⚠️ 只在 X11 后端生效（display 名字以 `:` 开头）；读不出来就回退 GDK 的读法，行为不倒退。⚠️ 闭包抓**弱引用**（`glib::WeakRef`），别把控件钉死 |
| 拖拽上传修复 + 「粘贴上传」（阶段 100） | 用户报「拖拽上传似乎没作用」。根因**不在本程序的判断逻辑**，在 GTK：同步版 `gtk::DropTarget` 在拖拽进入时把 `GdkDrop` 存进 `self->drop`，而它读数据是**异步**的 ⇒ 源端不应答时 `self->dropping` 永远 TRUE、旧 `self->drop` 永远留着 ⇒ GTK 下次拖拽进入直接 `if (self->drop != NULL) return;` ⇒ **这个控件上此后所有拖拽全部失灵**（症状：每个 motion 报 `assertion 'self->drop == drop' failed`，事件被丢弃）。⇒ 全部改用 `gtk::DropTargetAsync`（拖拽**离开**时清 `self->drop`，且没有 `dropping` 中间态）；顺带**自己按 mime 判定接不接、自己选读取类型**（同步版只认 GType ⇒ 同进程内「只给 mime 的源」与「要 GType 的目标」匹配不上，**远程列表 → 本地列表的下载拖拽从来没协商成功过**）；读数据加 **5 秒超时**（GTK 的选区输入流没有超时，源端不应答时会永远挂着，用户看到的现象和「拖拽没触发」一模一样 ⇒ 必须明确说「没拿到文件数据，请改用「上传…」」）。⚠️ **源侧的限制改不了**：X11 上拖拽传文件要源程序提供 `XdndSelection` 转换数据，而 **Deepin 文件管理器（dde-file-manager / Qt）声明了 XDND 类型却从不提供数据**（实测拖拽全程对任何 atom 的 `XConvertSelection` 都回 `property=None`，含 `TARGETS`/`text/uri-list`/`UTF8_STRING`/`text/plain`，CurrentTime 与拖拽中的新鲜服务器时间戳都试过）⇒ **任何 GTK 程序都拿不到它的拖拽文件**；对照实验：另一个 GTK4 程序跨进程拖进来能完整读到 `file:///…` ⇒ GDK 读数据路径没问题。⇒ 兜底：远程列表右键「**粘贴上传**」（读剪贴板 `text/uri-list`，`gdk::Clipboard::read_async`；同一个文件管理器的**剪贴板是好的**）。⚠️ 闭包一律抓**弱引用**；空拖拽给**可见提示**不再静默 |

| 数据库工作台（8.x，7.2 的形态升级） | 窗口改成**对象浏览器 + 多结果页签 + 可编辑数据网格**（对标 DBeaver / Navicat）。**左侧对象树**：模式 → 表/视图 → 列/索引，**展开才查**（懒加载，一上来不拉全库元数据），双击表开数据页签，右键可复制表名。**没查子节点的行先挂一个「载入中…」占位子节点**——GTK4 里没有子节点的行既不画展开箭头、`expand_row()` 也不发 `row-expanded`（实测），不挂占位子节点懒加载永远触发不了（症状就是"连上了但树里什么都没有"）；真数据回来后摘掉占位并把父行重新展开（摘占位会让 GTK 把父行折叠掉，折叠状态下展开子行是静默无效的）。**多页签**：每次执行 SQL 开一个新页签，标题取 SQL 摘要；页签与 worker 请求用 id 对应（`pending` 表），并发查询/翻页不会串页签。**表结构页签（对标 Navicat 的表设计器）**：对象树右键「表结构」开一页，内含字段（类型/可空/主键/默认值）/ 索引 / 外键 / **DDL** 四页签；DDL 由 information_schema **自己拼**（PG 没有 `SHOW CREATE TABLE`，默认值必须带上否则用户看一眼再执行就把默认值弄没了），可编辑并显式执行（MySQL 的 DDL 会自动提交，tooltip 里写明）；外键查询**按方言分派**（`constraint_column_usage` 是 PG 专有表，MySQL 查它会报 Unknown table）。**导出 INSERT SQL 脚本**（Navicat 的 "Export SQL"）：结果表工具栏「导出…」菜单里的「导出为 INSERT SQL 脚本…」，值按列类型转义（数字不带引号、布尔写 TRUE、文本按方言转义）。**插入 / 删除行**（9.4）：结果表工具栏加「插入行」「删除行」，**自动进入编辑模式**（不在编辑模式先开事务，事务开成功了才落到网格上）；新行里用户**没碰过的列不出现在 INSERT 语句里**，交给数据库用默认值（自增 id、默认时间）；删除是"标记"（立刻从网格消失，但点「保存修改」前库里不动，点「放弃」可恢复）；语句顺序 **INSERT → UPDATE → DELETE**（新行撞唯一约束时在 INSERT 阶段就失败并整体回滚，而不是先删旧行）；提交成功后**自动重新查表刷新**（自增 id 与默认值只有数据库知道）。**例程与触发器**（9.3）：展开模式时同时查表 / 函数 / 存储过程 / 触发器（各占独立懒加载槽位，某类失败只重查那一类），例程元数据**按方言分派**（PG 在 `pg_proc`，MySQL 在 `information_schema.ROUTINES`），PG 的同名重载靠**名字 + 身份参数**（`pg_get_function_identity_arguments`）区分；双击例程或触发器开**定义页签**（带 SQL 高亮的可编辑定义文本 + 「复制定义」「执行定义」），执行定义**逐条发完整语句**（函数体里的 `;` 不能拆、MySQL 服务端在多语句协议下也照分号切），PG 例程靠 `CREATE OR REPLACE` 幂等、触发器与 MySQL 例程先 `DROP … IF EXISTS`，MySQL `SHOW CREATE` 带的 `DEFINER=` 执行前去掉（换身份执行会因缺 SUPER 权限失败）。**结果表增强**：点列头排序（NULL 当最大值，跟 SQL 一个语义）、行内筛选、导出 CSV（带 BOM，Excel 友好，菜单入口见「导出格式扩展」一行）、右键复制名称。**数据编辑是显式动作**：点「编辑」才开事务、才允许改单元格；「保存修改」逐行拼 UPDATE（WHERE 用主键，无主键则用整行原值）执行，**全部成功才 COMMIT，任何一条失败就 ROLLBACK**，绝不自动提交；视图不能编辑；新值按列类型转字面量（整数/数字/布尔本地校验，填错报中文原因）。**SQL 编辑器带语法高亮**（复用 `panel/syntax.rs` 的分词器，tag 规则只有一份）。窗口按标签一份、hide-on-close。**能力边界**：仍只有 PostgreSQL / MySQL 两种（SQLite / SQL Server / Oracle 另议）；元数据走 `information_schema`（两家通用，不碰私有系统表）；结果排序筛选是**客户端**行为，只作用于已取回的行，不回服务器重查 |

| 事件对象（9.3 事件 Event） | 对象树补齐**定时事件**（Event）。**定时事件只有 MySQL 有**（Event Scheduler：`CREATE EVENT … ON SCHEDULE EVERY …` + `information_schema.EVENTS` + `SHOW CREATE EVENT`）。**PostgreSQL 压根没有这个功能**——它有的是 `pg_event_trigger` / `CREATE EVENT TRIGGER`，那是 **DDL 钩子**（在 DDL 执行前后触发一个函数），名字像、性质完全不同；定时任务在 PG 上得靠 `pg_cron` 之类扩展。查过 PG 9.6 / 10 / 12 / 17 / 18 五个版本的官方系统目录清单，里面**只有 `pg_event_trigger`，从来没有 `pg_event`**，`CREATE EVENT` 与 `pg_get_eventdef` 也从来不是 PG 的语法。所以 PG 一律不发事件请求（`dbmeta::proto_supports_events`）→ 树上不出现事件节点，**也不报「读元数据失败」**（硬查 `pg_event` 只会得到 `relation "pg_event" does not exist`）。**一个教训**：最初的实现按「PG 18 移除了定时事件、PG 10~17 才有」写了版本门槛（`SHOW server_version_num`），可那样在 **PG 12/14/16 上照样会炸**——那些版本同样没有 `pg_event`，门槛一放行就报错；靠「某版本 404」推断「其它版本有」不成立，得查目录清单。门槛机制已整块删掉。**挂载位置**：MySQL 的事件属于某个库 → 挂在**库（= schema）**节点下与表平铺（Navicat 的形状）。MySQL 的元数据**只查跨版本稳定的列**（`information_schema.EVENTS` 里 `SCHEDULING_TYPE`/`EVENT_TYPE` 只有 5.7/8.0 有，26.x 没有），用各家都有的 `INTERVAL_VALUE`/`INTERVAL_FIELD`/`STATUS`，节点说明列写「事件 · 1 DAY · ENABLED」；调度信息保留 MySQL 原文（`1 DAY`、`12 HOUR`），不翻译——`EVERY`/`AT`/`STARTS…ENDS…` 种类多，翻译反而丢信息。双击开**定义页签**（与例程/触发器同款），执行定义时先 `DROP EVENT IF EXISTS` 再 `CREATE`（事件没有 `OR REPLACE`）。**顺手修好一个跨版本隐患**：`SHOW CREATE EVENT` 在 MySQL 26.7 中间插了 `time_zone` 一列，原来"按固定下标取第 2 列当定义"会取错，`pick_def_text` 改成**按内容找"以 CREATE 开头的那一列"**——触发器/例程在新版 MySQL 上的同类问题一起修好 |
